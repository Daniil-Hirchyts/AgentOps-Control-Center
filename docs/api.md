# API reference

This is a readable companion to [`contracts/CONTRACT.md`](../contracts/CONTRACT.md), which remains the source of truth.
The live, machine-readable version is served by the backend:

- Swagger UI: <http://localhost:8080/api/docs> (or <http://localhost:5173/api/docs> through the Vite proxy)
- OpenAPI 3.1 JSON: <http://localhost:8080/api/openapi.json>

## Conventions

- JSON bodies, **camelCase** fields, `i64` IDs, RFC 3339 UTC timestamps generated by the server.
- Authenticated endpoints need `Authorization: Bearer <accessToken>`. Missing, invalid or expired token → `401`.
- Errors always look like:

  ```json
  {"error": {"code": "validation_error", "message": "contenu must be 1-4000 characters"}}
  ```

  | Code | Status |
  |---|---|
  | `bad_request` | 400 |
  | `unauthorized` | 401 |
  | `forbidden` | 403 |
  | `not_found` | 404 |
  | `conflict` | 409 |
  | `validation_error` | 422 |
  | `rate_limited` | 429 |
  | `internal` | 500 |
  | `llm_unavailable` | 503 |

- University endpoints (`/api/utilisateurs`, `/api/messages/...`) return plain JSON arrays.
  AgentOps lists return `{"items": [...], "total": n, "limit": 50, "offset": 0}` and accept `?limit=` (max 200) and `?offset=`.

The examples below use a shell variable for the base URL and `jq` to extract tokens:

```bash
API=http://localhost:8080
```

User IDs in the examples (alice = 1, bob = 2) are illustrative; check `GET /api/utilisateurs` after seeding.

## Accounts and authentication

### `POST /api/comptes` — create an account (public)

```bash
curl -s -X POST $API/api/comptes \
  -H 'Content-Type: application/json' \
  -d '{"username":"erin","password":"demo-password-123","role":"OPERATOR"}'
```

`201` → `{"id":5,"username":"erin","role":"OPERATOR","createdAt":"2026-11-06T10:00:00Z"}`.
`role` is optional (default `OPERATOR`). Username: 3–32 chars of `[A-Za-z0-9_.-]`, case-insensitively unique (`409` if taken).
Password: 8–128 chars.

### `POST /api/auth/login`

```bash
curl -s -c cookies.txt -X POST $API/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"demo-password-123"}' | tee login.json
TOKEN=$(jq -r .accessToken login.json)
```

`200` → `LoginResponse`:

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "user": {"id": 1, "username": "alice", "role": "OPERATOR", "online": false, "createdAt": "..."}
}
```

Also sets the `agentops_refresh` cookie (HttpOnly, SameSite=Strict, Path=/api/auth). Wrong credentials → `401`.

### `POST /api/auth/refresh` and `POST /api/auth/logout`

Both are authenticated by the refresh cookie and require the anti-CSRF header.

```bash
curl -s -b cookies.txt -c cookies.txt -X POST $API/api/auth/refresh -H 'X-Requested-With: agentops'
curl -s -b cookies.txt -X POST $API/api/auth/logout -H 'X-Requested-With: agentops' -o /dev/null -w '%{http_code}\n'  # 204
```

Refresh returns a new `LoginResponse` and rotates the cookie. Logout revokes the refresh token.

### `GET /api/auth/me`

```bash
curl -s $API/api/auth/me -H "Authorization: Bearer $TOKEN"
```

### `POST /api/auth/ws-ticket`

```bash
TICKET=$(curl -s -X POST $API/api/auth/ws-ticket -H "Authorization: Bearer $TOKEN" | jq -r .ticket)
```

`{"ticket": "...", "expiresIn": 30}`. A JWT with audience `ws`, valid 30 s, only accepted by the WebSocket upgrade.

## Messaging (university endpoints)

### `GET /api/utilisateurs`

```bash
curl -s $API/api/utilisateurs -H "Authorization: Bearer $TOKEN"
```

```json
[
  {"id": 1, "username": "alice", "role": "OPERATOR", "online": true,  "createdAt": "..."},
  {"id": 2, "username": "bob",   "role": "REVIEWER", "online": false, "createdAt": "..."}
]
```

All users, the caller included, with live presence (`online` = at least one open WebSocket).

### `GET /api/messages/{utilisateurId}`

```bash
curl -s "$API/api/messages/2?limit=50" -H "Authorization: Bearer $TOKEN"
```

```json
[
  {"id": 41, "expediteurId": 2, "destinataireId": 1, "contenu": "Salut Alice", "dateEnvoi": "2026-11-06T10:14:02Z"},
  {"id": 42, "expediteurId": 1, "destinataireId": 2, "contenu": "Bonjour !",   "dateEnvoi": "2026-11-06T10:15:30Z"}
]
```

Conversation between the caller and `utilisateurId`, oldest first. `limit` default 200, max 500. `beforeId` loads older
pages (messages with `id < beforeId`). Unknown user → `404`.

## AgentOps

### Cases (OPERATOR)

```bash
curl -s -X POST $API/api/cases -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{
  "title": "Invoice INV-2026-0042 from Northwind",
  "invoice": {
    "invoiceNumber": "INV-2026-0042",
    "vendor": "Northwind Supplies",
    "amount": 48750.00,
    "currency": "EUR",
    "issueDate": "2026-11-02",
    "description": "Consulting services, October (urgent payment requested to a new IBAN)",
    "historicalAverage": 4200.00
  }
}'
```

`201` → `CaseDto` with `status: "OPEN"`.

- `GET /api/cases` → `Page<CaseDto>` of the caller's own cases.
- `GET /api/cases/{id}` → owner operator, or a reviewer assigned to one of its runs.

### Agent runs

```bash
curl -s -X POST $API/api/agent-runs -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"caseId": 1, "reviewerId": 2}'
```

`202` → `AgentRunDto` with `status: "PENDING"`. Processing is asynchronous; follow progress with `agent_status` WebSocket
events or by polling `GET /api/agent-runs/{id}`. `reviewerId` must be a `REVIEWER` other than the caller.

- `GET /api/agent-runs?status=AWAITING_APPROVAL&caseId=1` → `Page<AgentRunDto>`. Operators see runs they created,
  reviewers see runs assigned to them.
- `GET /api/agent-runs/{id}` → creator or assigned reviewer only.

Example `AgentRunDto` after analysis:

```json
{
  "id": 7, "caseId": 1, "caseTitle": "Invoice INV-2026-0042 from Northwind",
  "status": "AWAITING_APPROVAL", "modelIdentifier": "mock", "llmMode": "mock",
  "inputSnapshot": {"invoiceNumber": "INV-2026-0042", "amount": 48750.0, "...": "..."},
  "output": {
    "riskLevel": "high",
    "reasoningSummary": "Amount is 11x the vendor's historical average and the description asks for payment to a new bank account.",
    "recommendedAction": "flag_invoice_for_review",
    "requiresApproval": true
  },
  "error": null, "attempts": 1, "reviewerId": 2, "createdBy": 1,
  "createdAt": "...", "updatedAt": "...",
  "approval": {"id": 5, "status": "PENDING", "...": "..."}
}
```

### Approvals

- `GET /api/approvals?status=PENDING` → `Page<ApprovalDto>`. Reviewers see approvals assigned to them, operators see the
  ones they requested.
- `GET /api/approvals/{id}` → assigned reviewer or requester.
- `POST /api/approvals/{id}/decision` → assigned `REVIEWER` only.

```bash
BOB=$(curl -s -X POST $API/api/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"bob","password":"demo-password-123"}' | jq -r .accessToken)

curl -s -X POST $API/api/approvals/5/decision -H "Authorization: Bearer $BOB" -H 'Content-Type: application/json' \
  -d '{"decision":"approve","reason":"Checked with vendor by phone"}'
```

`200` → updated `ApprovalDto`. A second decision on the same approval → `409 conflict`. A different reviewer → `403`.
`reason` is optional, at most 1000 characters.

### Audit log

```bash
curl -s "$API/api/audit-events?agentRunId=7" -H "Authorization: Bearer $TOKEN" | jq '.items[] | {eventType, actorUsername, createdAt}'
```

Event types: `run_created`, `run_status_changed`, `llm_request`, `llm_response_valid`, `llm_response_invalid`,
`llm_error`, `approval_requested`, `approval_decided`, `action_executed`, `action_skipped`, `run_recovered`.

### Health and LLM

```bash
curl -s $API/api/health
# {"status":"ok","database":"ok","llm":{"mode":"mock","provider":"lmstudio","model":"mock","reachable":null}}

curl -s $API/api/llm/models -H "Authorization: Bearer $TOKEN"   # OPERATOR only
# {"mode":"real","baseUrl":"http://localhost:1234/v1","configuredModel":"","models":["qwen2.5-7b-instruct"],"reachable":true}
```

## WebSocket `/ws/messages`

Connect with a fresh ticket: `ws://localhost:8080/ws/messages?ticket=<ticket>` (or `ws://localhost:5173/ws/messages?...`
through Vite). The upgrade returns `401` for a missing/expired ticket and `403` for a disallowed `Origin`.

Using [websocat](https://github.com/vi/websocat). The `Origin` header is required by the server's Origin check:

```bash
TICKET=$(curl -s -X POST $API/api/auth/ws-ticket -H "Authorization: Bearer $TOKEN" | jq -r .ticket)
websocat -H 'Origin: http://localhost:5173' "ws://localhost:8080/ws/messages?ticket=$TICKET"
```

Then type one JSON object per line:

```json
{"type":"message","destinataireId":2,"contenu":"Bonjour !","clientMessageId":"c0ffee-1"}
{"type":"typing","destinataireId":2,"isTyping":true}
```

`expediteurId` and `dateEnvoi` may be included (as in the assignment's sample message) but are ignored: the sender comes
from the ticket and the timestamp from the server. `contenu` is trimmed and must be 1–4000 characters; the recipient
must exist and differ from the sender.

Events you will receive:

```json
{"type":"message","id":42,"expediteurId":1,"destinataireId":2,"contenu":"Bonjour !","dateEnvoi":"2026-11-06T10:15:30Z","clientMessageId":"c0ffee-1"}
{"type":"user_presence","userId":2,"username":"bob","online":true}
{"type":"typing","expediteurId":2,"destinataireId":1,"isTyping":true}
{"type":"agent_status","runId":7,"caseId":1,"status":"AWAITING_APPROVAL","updatedAt":"..."}
{"type":"approval_requested","approvalId":5,"runId":7,"caseId":1,"caseTitle":"...","riskLevel":"high","proposedAction":"flag_invoice_for_review","requestedBy":1,"createdAt":"..."}
{"type":"approval_resolved","approvalId":5,"runId":7,"status":"APPROVED","decidedBy":2,"decidedAt":"..."}
{"type":"error","code":"rate_limited","message":"too many messages","clientMessageId":"c0ffee-9"}
```

Who receives what:

| Event | Recipients |
|---|---|
| `message` | all recipient connections + all sender connections (echo with authoritative `id` and `dateEnvoi`) |
| `user_presence` | everyone connected |
| `typing` | recipient only |
| `agent_status` | run creator + assigned reviewer |
| `approval_requested`, `approval_resolved` | assigned reviewer + requester |
| `error` | the connection that caused it |

Limits: frames ≤ 16 KiB; 10 client messages per 5 s per connection; server ping every 25 s; the connection is closed
after 60 s without traffic. A user may have several connections (tabs, phone + laptop); they are online while at least
one is open.

Two-terminal test of offline delivery:

```bash
# Terminal 1: Alice is connected; Bob is not.
websocat -H 'Origin: http://localhost:5173' "ws://localhost:8080/ws/messages?ticket=$TICKET"
{"type":"message","destinataireId":2,"contenu":"Tu verras ça plus tard"}

# Terminal 2: later, Bob reads the history over REST.
curl -s $API/api/messages/1 -H "Authorization: Bearer $BOB" | jq '.[-1]'
```
